## Constat de départ (code de main, 2026-10-09)

1. `bootstrap.ts` ligne 213 : `appVersion = syncPlatform && desktop ? desktop.getVersion() : '0.0.0'`. Sur iPhone `desktop` est `null` : le service de synchro publie `0.0.0`. Y-07 (écran de version, bandeau « Mettez à jour l'app » côté PC) est donc faussé entre PC et iPhone. **Dette à solder ici.**
2. `AboutSection` n'affiche la version que si `desktop` existe : l'iPhone ne montre pas sa version (decisions P-05 : « version et mise à jour sur PC seulement »). Sans numéro lisible, impossible de vérifier qu'une mise à jour a pris.
3. `build-ios.yml` publie les notes `CircleTasks ${VERSION}` : jamais de vraies notes dans SideStore (le PC, lui, prend la section de `CHANGELOG.md`). Critère PRD « nouvelle version visible avec ses notes » non tenu.
4. `migrate()` d'une base **plus récente** que l'app (retour à une ancienne IPA) lève `Base en version N, inconnue de cette version de l'app` : diagnostic brut, aucune action. Impasse à fermer.
5. Rien ne lie encore la mise à jour au replanning des notifications, au signet et au Trousseau par un test : N-05 A3, Y-IOS-01 A5 sont seulement des contrôles d'appareil.

## Décisions recommandées (à valider par Ali)

- D1 — **Source unique de la version** : un module `src/platform/appVersion.ts` (`getVersion` de `@tauri-apps/api/app`, valeur de `tauri.conf.json`), utilisé par `bootstrap.ts` pour **PC et iPhone**, par « À propos » et par le diagnostic. Le champ `getVersion` de `DesktopPlatform` reste (D-03) mais délègue au module. Aucune commande Rust, aucune capability nouvelle (`core:default`). Échec de lecture : `0.0.0` n'est **plus** une valeur de repli silencieuse : la synchro publie `null` (champ facultatif, Y-07 D2 : « texte seul »), l'échec est journalisé (code seul) et « À propos » affiche « Version inconnue ».
- D2 — **« À propos » iPhone** : ligne « CircleTasks {version} » (sans « Rechercher une mise à jour », qui reste réservée au PC). Modifie la décision P-05 « version sur PC seulement » : **proposition de mise à jour du PRD M16 / decisions, non décidée seule**.
- D3 — **Notes de version** : section de `CHANGELOG.md` dont le titre est `## [X.Y.Z]` ou `## X.Y.Z`, même extraction que `build-windows.yml` (factorisée dans un script partagé, un seul code pour les deux plateformes), mise dans `localizedDescription` de la version et dans la page de la release GitHub ; repli `CircleTasks X.Y.Z` **avec avertissement `::warning::`** visible dans le résumé du run (un tag sans entrée de CHANGELOG ne passe plus inaperçu). Notes en français, une ligne par changement visible pour l'utilisateur, aucun nom de tâche ni donnée personnelle.
- D4 — **Réglage local `app.lastLaunchedVersion`** (portée `local`, jamais synchronisé, clé déclarée dans le registre des réglages) : écrit à la fin d'un démarrage réussi. Un changement de valeur au démarrage = « premier lancement d'une nouvelle version » : (a) replanification complète des rappels (critère 9), (b) une ligne de journal technique `app-updated` avec les deux numéros (jamais de contenu), (c) rien d'affiché si tout va bien (aucune boîte « bienvenue »). Absent = première installation : pas de mise à jour.
- D5 — **Pas de retour arrière** : SideStore ne rétrograde pas proprement. Le guide le dit ; l'app, elle, refuse d'ouvrir une base plus récente sans rien toucher et indique la marche à suivre (critère 11).
- D6 — **Numéro de build** : `CFBundleVersion` de l'IPA N+1 est strictement supérieur à celui de N (SideStore compare `version` puis `buildVersion`) ; la CI échoue sinon.

### Source SideStore avec deux versions

1. **[N]** **Étant donné** un `source.json` existant contenant la version N (ex. 0.2.3) et un Info.plist d'IPA N+1 (0.3.0, `CFBundleVersion` supérieur), **quand** `make-source-json.mjs` est lancé, **alors** le fichier contient **deux** entrées dans `versions`, N+1 en premier (tri par numéro, pas par date), les champs d'app hérités (`version`, `versionDate`, `downloadURL`, `size`) sont ceux de N+1, N reste intacte (URL, `sha256`, `size`, date), le `bundleIdentifier` est identique, `iconURL` est présent, et republier N+1 remplace seulement sa propre entrée (déjà couvert par I-01 critère 3 pour une version : le test ajoute le cas « publication d'un correctif N+0.0.1 après N+1 : il ne passe pas devant »).
2. **[N]** **Étant donné** la source à deux versions, **alors** un contrôle de cohérence (nouveau, `scripts/ios/check-source.mjs`, aussi lancé par la publication avant le push) échoue si : `CFBundleVersion` de N+1 ≤ celui de N (D6), `minOSVersion` de N+1 supérieur à iOS 18 sans note, `downloadURL` ≠ `ipaUrlFor(version)`, `sha256` ou `size` absents, `localizedDescription` égale au repli sans CHANGELOG (avertissement, pas échec, D3), `bundleIdentifier` ≠ `fr.circletasks.planner`.
3. **[N]** **Étant donné** un `CHANGELOG.md` de test avec `## [0.3.0]` (3 lignes) et `## 0.2.3`, **quand** le script d'extraction des notes est lancé pour `0.3.0`, **alors** il rend exactement les 3 lignes ; pour `0.9.9` il rend vide et signale l'absence ; la sortie sert aux deux workflows (test d'équivalence avec l'extraction de `build-windows.yml`, ou remplacement de celle-ci par le script commun).
4. **[N]** **Alors** un test de cohérence relit : `bundle.identifier` de `tauri.conf.json`, `CFBundleIdentifier` attendu par `build-ios.yml`, `bundleIdentifier` du gabarit `source.template.json`, `VAULT_SERVICE` du Trousseau (`vault.rs`) et le préfixe de signet de Y-IOS-01 : **tous identiques et inchangés** entre N et N+1 (ADR 0001 : l'identifiant ne change plus). Un changement fait échouer le test avec le message « la mise à jour perdrait les données ».
5. **[CI]** `build-ios.yml` sur la branche du lot : l'étape de publication simulée (`publish=false`) construit la source avec l'IPA de la branche et la source N publiée, lance `check-source.mjs` et écrit dans le résumé : version, build, notes extraites (première ligne), « source valide ». Aucune publication hors tag `ios-v*` (I-01 inchangé).

### Migrations, données, signet, Trousseau, notifications

9. **[U]** **Premier lancement de N+1 sans perte.** **Étant donné** une base **peuplée à la version de schéma N** (migrations de `migrations` sans la dernière, plus une migration additive de test ; tâches, routines, projets, réglages, `sync_unknown` non vide, deux espaces) et `app.lastLaunchedVersion = 0.2.3`, **quand** `bootstrapApp` démarre avec la version `0.3.0`, **alors** : la sauvegarde avant migration est demandée **une fois, avant** la première migration ; les migrations en attente s'appliquent dans l'ordre ; **chaque table contient les mêmes lignes qu'avant** (comptage et contenu par somme de contrôle, hors colonnes ajoutées) ; les réglages (dont `device.id`, filtre Pro/Perso/Tout, thème, verrou Face ID) sont identiques ; `sync_outbox` est vide ; `app.lastLaunchedVersion` = `0.3.0` ; deuxième démarrage : aucune sauvegarde, aucune migration, aucun `app-updated`. Une seule sauvegarde « Avant mise à jour » est ajoutée à la liste de P-04.
10. **[U]** **Signet de dossier et clé du Trousseau conservés.** **Étant donné** le même démarrage avec un faux `BookmarkFs` portant un signet valide et un faux Trousseau portant la clé `circletasks.sync.key.v1`, **alors** après la mise à jour : le signet est relu sans nouvelle demande (état « dossier joignable », aucun sélecteur ouvert), la clé n'est ni réécrite, ni supprimée, ni régénérée (aucun appel `set` / `delete` du faux Trousseau), `sync_state` et le curseur de lecture sont inchangés, le cycle de synchro reprend. **Étant donné** un signet devenu invalide (iOS le déclare périmé), **alors** la ligne de Réglages et le bandeau disent « Choisissez de nouveau le dossier iCloud Drive/CircleTasks » (Y-IOS-01), la file locale attend sans perte, la clé est conservée : **jamais** une régénération silencieuse. Le Trousseau absent alors que la synchro est configurée : état visible « Clé introuvable : associez de nouveau l'appareil » (Y-08/Y-11), jamais une page blanche.
11. **[U]** **Notifications replanifiées.** **Étant donné** `app.lastLaunchedVersion` ≠ version courante et un registre local de notifications contenant des identifiants, **quand** le démarrage réussit, **alors** le déclencheur `open` de N-05 est exécuté en mode **complet** (comme registre perdu, N-05 critère 4) : le faux planificateur reçoit le plan recalculé, sans doublon, l'identifiant réservé 1 (fin de Focus) et 2 (alerte d'expiration, I-02) sont reposés, le plafond de 64 est respecté ; si `get_pending` rend déjà exactement le plan, aucune notification n'est annulée puis reposée inutilement. Échec de planification : le bandeau N-01 (`schedule-failed`) apparaît, pas de silence.
12. **[U]** **Mise à jour interrompue.** **Étant donné** un démarrage de N+1 interrompu après la migration 1 sur 2 (fermeture simulée), **alors** le démarrage suivant reprend à la migration 2 (chaque migration est transactionnelle), `app.lastLaunchedVersion` n'a pas été écrit, la sauvegarde « Avant mise à jour » n'est pas dupliquée si elle existe déjà pour cette version de départ, aucune ligne perdue.

### Aucun échec silencieux, aucune impasse

13. **[U]** **Migration en échec après la mise à jour.** **Étant donné** une migration de test qui échoue (instruction invalide), **alors** : la base reste à la version N (transaction annulée), l'écran d'échec affiche le diagnostic existant avec **l'étape « migration {n} »**, le nom de l'erreur, **la version de l'app et la version de schéma de la base** (`schema_migrations`), le chemin de la base ; et, nouveauté, **trois actions** : « Réessayer », « Copier le détail » (existants) et « Restaurer la sauvegarde d'avant la mise à jour » (visible seulement si la sauvegarde de ce démarrage existe, via le service de P-04-iOS, avec confirmation « Annuler » par défaut) ; plus la phrase « Vos données sont intactes. Ne supprimez pas CircleTasks. Envoyez le détail pour obtenir un correctif. » Journal technique : `db: migration {n} impossible ({nom})`, sans contenu (I-04). Sauvegarde impossible (disque plein) : aucune migration n'est lancée, `dbBackupFailed` est affiché avec l'action « Réessayer » (déjà couvert par D-03, le test vérifie qu'il l'est sur `ios`).
14. **[U]** **Base plus récente que l'app** (D5). **Étant donné** `schema_migrations` contenant une version inconnue du code, **alors** `migrate()` lève une erreur **typée** (`SchemaNewerThanApp`, version de la base et version connue), rien n'est écrit, et l'écran dit : « Cette version de CircleTasks est plus ancienne que vos données. Installez la dernière version depuis SideStore. Vos données ne sont pas modifiées. » avec « Copier le détail » ; pas de bouton de restauration dans ce cas. Les messages bruts `Base en version N, inconnue…` ne s'affichent plus tels quels.
15. **[U]** **Réintégration en échec après la mise à jour** (Y-07 critère 6 / dette « échec de réintégration ») : une ligne de `sync_unknown` qui ne peut pas être réintégrée garde la synchro active et affiche, sur iPhone, la ligne de Réglages et le bandeau Y-07 (`reintegrationFailure`), disparus après une réintégration réussie au démarrage suivant. Test avec la plateforme `ios`.
16. **[U]** **Version incohérente.** `app.lastLaunchedVersion` plus grand que la version courante (retour à une IPA plus ancienne dont la base est pourtant compatible) : journal `app-downgraded` et la ligne « À propos » reste exacte ; aucune migration inverse, aucune donnée supprimée.
17. **[E]** Projet `iphone`, base préremplie à la version N injectée, version `0.3.0` simulée : l'app s'ouvre sur Aujourd'hui avec les tâches créées avant ; « À propos » montre `0.3.0` ; échec de migration injecté : l'écran d'échec avec ses trois actions et sans page blanche ; base plus récente injectée : le message du critère 14.

## Critères seulement vérifiables sur l'appareil (reportés dans `_checklist-ordre-5.md`, phase 4)

Procédure de référence, avec deux IPA produites par `build-ios.yml` : **N** = IPA candidate sans la dernière migration de test, **N+1** = IPA candidate publiée en suivant (tag `ios-v*` ou source de test dans circletasks-releases) avec une migration additive.

- A1. **Installer N** depuis la source SideStore (ajoutée une fois), noter la version dans « À propos ».
- A2. **Créer des données** : 3 tâches (une datée avec rappel à +2 jours, une routine, une dans l'espace Perso), un réglage changé (thème sombre), Face ID activé, dossier iCloud choisi, appareil associé au PC, une tâche créée sur le PC reçue sur l'iPhone, rappel planifié (« Planifiés jusqu'au… »). Noter le nombre de notifications en attente.
- A3. **Publier N+1** ; dans SideStore, la source affiche N+1 **avec ses notes** (relever le texte) ; « Mettre à jour » en un geste ; durée notée.
- A4. **Premier lancement de N+1** : verrou Face ID demandé (I-03, la mise à jour ne le contourne pas), puis Aujourd'hui avec les mêmes tâches, filtre et thème conservés ; « À propos » = N+1 ; aucun bandeau d'erreur, aucune fenêtre d'accueil.
- A5. **Signet et clé** : Réglages > Synchronisation sans nouvelle demande de dossier ; une tâche créée sur le PC arrive, une tâche créée sur l'iPhone arrive sur le PC ; la clé n'est pas redemandée. Si SideStore a réinitialisé le signet : l'invitation « Choisissez de nouveau le dossier » est affichée et la file attend (noter).
- A6. **Notifications** : rappel planifié avant la mise à jour toujours reçu à l'heure (≤ 60 s) ; nombre en attente égal ou replanifié (noter lequel, voir N-05 A3), aucun doublon ; actions « Fait » et « +15 min » fonctionnent encore (N-03 A2 étendu (d)) ; alerte d'expiration remplacée (I-02).
- A7. **Y-07 réel** : mettre l'iPhone à jour avant le PC avec une migration additive : le PC affiche « Mettez à jour l'app » avec le numéro réel de l'iPhone (pas `0.0.0`) et continue de lire ; mettre le PC à jour (installeur) ; le bandeau disparaît, le champ créé sur l'iPhone est présent sur le PC.
- A8. **Sauvegarde** : la liste de P-04 contient une sauvegarde « Avant mise à jour » datée de A3.
- A9. **Échec** (build de test dédié, jamais l'IPA candidate finale) : une migration volontairement invalide : l'écran d'échec avec étape, versions, trois actions ; « Restaurer la sauvegarde d'avant la mise à jour » rend les données ; réinstaller l'IPA correcte : tout est là. Puis base plus récente : installer à nouveau N par-dessus N+1 : message du critère 14, aucune donnée touchée, réinstaller N+1 : tout est là.
- A10. **Sans effacer** : l'app n'a pas été supprimée ni réinstallée à aucun moment (sinon A5, A6 sont à refaire : les données locales sont perdues, le guide le dit).
