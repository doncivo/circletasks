### Action et confirmation

1. **Étant donné** une synchro configurée avec clé et au moins un autre appareil dans APPAREILS (statut différent de `forgotten`), **quand** j'ouvre Réglages > Synchronisation > Détails, **alors** chaque ligne d'un **autre** appareil porte « Oublier cet appareil » ; la ligne de l'appareil local n'en a pas (§14.2).
2. **Quand** je touche « Oublier cet appareil », **alors** `ForgetDeviceDialog` (composé de `ConfirmDialog`, aucun élément visuel nouveau) nomme l'appareil (même nom que dans APPAREILS) et explique avant tout envoi : l'appareil ne sera plus lu au-delà d'un point commun à tous ; ses fichiers seront supprimés d'iCloud (récupérables 30 jours dans « Supprimés récemment » d'iCloud, ADR §14.1) ; **l'oubli ne s'annule pas** et l'appareil devra être associé de nouveau ; « Annuler » est le bouton par défaut (§14.2).
3. **Quand** je confirme, **alors** `main` appelle `sync_device_forget({ deviceId })` : Rust ouvre la **confirmation native** (« Annuler » par défaut, fenêtre propriétaire `main` au premier plan, texte dans `src/i18n/native/fr.json`, mêmes préconditions et compteurs que Y-08) ; refus ou fermeture : message « Oubli annulé », **rien n'est écrit** ; application pas au premier plan : `not-foreground` ; trop de demandes : `rate-limited` ; aucune de ces issues n'ouvre de boîte bloquante de notre côté (§14.2, §2.1).
4. **Alors** l'écran de confirmation dit en une phrase que **l'appareil oublié garde sa copie des données et sa clé** : seule « Réinitialiser la synchronisation » (Y-11) coupe son accès aux données futures (§14.2 « Ce que Y-10 ne règle pas »).
5. **Alors** Rust refuse `sync_device_forget` (aucune boîte, aucune écriture) : sans dossier (`not-configured`) ; sans clé (`key-missing`) ; pour **l'appareil local** et pour un identifiant **inconnu** de `sync_state` (`bad-name`, code existant ; tout code nouveau serait ajouté à Rust et à `format.ts` avec le test croisé) ; pour un appareil **déjà oublié** : succès sans effet, idempotent (§14.2, §11.1).

### Marqueur, ordre total et coupure

6. **Étant donné** la confirmation acceptée, **alors** Rust inscrit la déclaration dans `sync/forgotten.json` (écriture `.tmp` + renommage) et reste **seul maître** de la liste `forgotten` publiée : le moteur republie son `state.ctx` avec `forgotten += { deviceId, at: <hlc>, lastAck }` (`lastAck` = dernier accusé connu de l'appareil, ou `null`) ; `sync_write_state` refuse (`state-mismatch`) un `forgotten` différent de la liste de Rust ; la règle « `forgotten` non vide refusé avant le lot Y4 » (Rust et `memory.ts`) est **levée** et remplacée par cette comparaison, test croisé Rust / mémoire sur la même table de cas ; 64 déclarations au plus (§14.2, §1.4, §11.1, §14.4).
7. **Ordre total** : **étant donné** des déclarations publiées par plusieurs appareils, **alors** `retention.ts` (pur) les trie par `at` (hlc, l'UUID départage) et les applique dans cet ordre ; une déclaration **émise par un appareil déjà oublié** par une déclaration antérieure est **sans effet** ; deux appareils qui s'oublient l'un l'autre : seule la plus ancienne compte ; la même déclaration lue deux fois, ou dans un autre ordre de lecture, donne le même résultat (test table-driven et test de propriété `fast-check`, sans délai) (§14.2).
8. **Coupure** : **alors** `cutoff(X)` est le **maximum des accusés de X** publiés par **tous** les appareils actifs non oubliés (et non le seul accusé de l'appareil qui oublie) ; chaque appareil lit X **jusqu'à `cutoff(X)`**, jamais au-delà ; ses enregistrements au-delà sont ignorés ; test de simulation à trois appareils : B avait lu X plus loin que A, A oublie X, puis les trois lisent : **A, B et C finissent avec exactement les mêmes écritures de X** ; le maximum peut croître tant qu'un appareil n'a pas appris l'oubli et est stable dès que tous les appareils actifs l'annoncent (§14.2).
9. **Alors** un `forgotten` lu dans un `state.ctx` qui n'est **pas authentifié avec la clé locale** (statut `foreign`, `corrupt`, `rollback`) est **ignoré** : un faux `state.ctx` étranger ne peut oublier personne ni couper personne ; test de simulation (§14.2, §14.3 dernier alinéa, tests de l'ADR §14.4).
10. **Effets chez tous les appareils** : **alors** l'appareil prend le statut `forgotten` dans `sync_state` et dans APPAREILS (libellé « Oublié », sans bouton) ; il **ne compte plus dans les accusés** de la purge (`activeDevices`) : une trace de suppression qu'il n'avait pas lue est purgée dès que les **autres** appareils actifs l'ont lue et que 30 jours se sont écoulés, sans attendre 180 jours (test avec l'horloge injectée, jamais d'attente réelle) ; le bandeau « Mettez à jour l'app » de Y-07 disparaît pour un appareil oublié (Y-07 critère 9) (§14.2).

### Suppression des fichiers de l'appareil oublié (avenant à la règle d'écrivain unique)

11. **Alors** un appareil actif **peut supprimer** les fichiers de `devices/<id oublié>/` (jamais écrire, renommer ni créer), et **seulement quand** : (1) le dossier est marqué oublié dans un `state.ctx` **authentifié** d'un appareil actif non oublié, par une déclaration **valide** selon l'ordre total ; (2) **tous les appareils actifs** ont accusé X jusqu'à `cutoff(X)` **et** accusé le `stateSeq` de l'état qui porte la déclaration ; Rust vérifie ces conditions dans une **commande dédiée** (`sync_delete_own` reste limitée au propre dossier de l'appareil, `names.rs` valide l'identifiant avant tout chemin) (§14.2, §14.4, §1.1).
12. **Alors** Rust **refuse** la suppression (code existant `state-mismatch`, rien n'est supprimé) dans chacun de ces cas, testés un par un : aucune déclaration authentifiée ; déclaration émise par un appareil lui-même oublié ; un appareil actif n'a pas encore accusé jusqu'à `cutoff(X)` ; un appareil actif n'a pas accusé le `stateSeq` de l'état qui porte la déclaration ; cible = l'appareil local ; identifiant mal formé ou hors `devices/` (`bad-name`) ; la suppression est **idempotente** : deux appareils qui suppriment en même temps, ou un fichier déjà absent, ne donnent aucune erreur ; aucun fichier d'un autre dossier n'est jamais touché (§14.2, §1.1, §11.1).
13. **Alors** la suppression se fait **au cycle** qui suit la réunion des conditions, sans nouvelle confirmation ; tant qu'elle n'est pas possible, la ligne de l'appareil oublié le dit : « Oublié · suppression des fichiers en attente de {appareil} » (nom de l'appareil qui n'a pas encore accusé), sans limite de durée et sans action automatique ; elle disparaît quand les fichiers ont disparu (D3).

### Reprise et aucun échec silencieux (exigence d'Ali)

14. **Alors** un oubli interrompu à n'importe quel instant reprend sans perte et sans doublon : arrêt avant l'inscription dans `forgotten.json`, entre l'inscription et la publication de `state.ctx`, entre la publication et la suppression ; au démarrage, `forgotten.json` (Rust) fait foi et le moteur republie ; test d'arrêt avant **chaque** écriture du scénario (même méthode que `joinInterrupt.test.ts`), puis un cycle : état final identique à celui d'une exécution sans arrêt (§14.2, §9 règle 1).
15. **Aucun échec silencieux** : tout échec ou état bloqué est **visible dans l'app** et **persiste jusqu'à sa résolution**, y compris après redémarrage : (a) un refus de Rust, `cloud-pending`, `folder-unreachable`, `vault-unavailable` ou tout autre code pendant l'oubli ou la suppression est écrit dans `sync_meta.forgetFailure` (`deviceId`, code, heure ; jamais de contenu, de clé ni de chemin) et affiché dans l'emplacement `forget` de l'écran de détails en rouge, `role="status"`, avec « Réessayer » ; effacé **seulement** à la réussite ; (b) l'état « suppression en attente » du critère 13 est lui aussi persistant et visible ; (c) un échec ne se limite jamais à un journal, à `console.*` ou à un `catch` vide (test qui échoue si un chemin d'erreur de `forget.ts` n'écrit pas `forgetFailure` ni ne propage l'erreur, y compris les refus de la boîte native hors annulation volontaire) ; (d) l'état est aussi porté par un **bandeau A-09** tant qu'il dure (voir A-09 critère 9 f) (exigence d'Ali).

### Appareil oublié qui revient

16. **Étant donné** un appareil X qui possède encore la clé et lit un `forgotten` authentifié qui contient son `device_id`, **alors** X **cesse de publier** (sa file d'envoi est gardée, rien n'est perdu ni écrit), **garde sa base**, prend la phase `forgotten` (valeur nouvelle de `SyncPhase`, `types.ts`) et affiche, dans Réglages et dans un bandeau A-09, « Cet appareil a été oublié : associez-le de nouveau » avec le bouton « Associer de nouveau » ; il ne lit plus rien non plus (§14.2).
17. **Quand** je touche « Associer de nouveau » sur X, **alors** (D2) : le dossier est délié sans effacer la clé, un **nouveau `device_id`** est créé, l'appareil est lié de nouveau (`sync_bind_device`, autorisé après l'oubli du dossier) et rejoint par la **reprise depuis l'instantané en fusion** (§5.5, `join.ts`) ; **rien n'est effacé** localement, ses données locales sont publiées sous son nouvel identifiant ; l'ancien `device_id` reste dans `forgotten` ; tout ceci est testé par simulation (appareil oublié qui revient avec des écritures non publiées : elles arrivent chez les autres sous le nouvel identifiant, jamais sous l'ancien) (§14.2, §10.3).

## Décisions (option recommandée ; lignes ajoutées à docs/decisions.md)

- D1 — Deux temps : `ForgetDeviceDialog` (explication, « Continuer ») puis confirmation native courte de Rust (« Annuler » par défaut). La boîte native protège contre une WebView compromise (ADR §2.1), la boîte de l'app porte le texte long ; un oubli irréversible mérite les deux.
- D2 — « Associer de nouveau » sur l'appareil oublié enchaîne : délier le dossier (clé gardée), nouveau `device_id`, reliaison, fusion. Le texte de l'ADR (§14.2) fixe le résultat (nouvel identifiant, fusion) ; l'enchaînement est la voie qui respecte `sync_bind_device` figé.
- D3 — Aucune échéance pour la suppression en attente : un appareil actif hors ligne pendant des mois retarde seulement la suppression (jamais l'oubli, qui est déjà effectif pour les purges), et la ligne le dit.
- D4 — **Écart avec l'ADR 0011 §11.1 et §14.4, à faire corriger par l'architecte** : le texte parle d'une « commande dédiée » pour la suppression des fichiers d'un appareil oublié, mais §11.1 et le lot Y4 ne comptent que deux commandes (`sync_device_forget`, `sync_reset_key`). Option recommandée : une **troisième commande** `sync_forgotten_delete({ deviceId })` (23 commandes `sync_*`), car `sync_delete_own` doit rester limitée à son propre dossier ; `build.rs`, `sync.json` et `config.rs` en tiennent compte.
- D5 — Une déclaration `forgotten` d'un `state.ctx` non authentifié est ignorée sans trace d'oubli (ADR §14.3, dernier alinéa, appliqué aussi à Y-10).
