## Ce qui est développable et testable sans compte

Aucun compte Google n'est requis pour livrer et tester tout le code : tout passe par une interface `CalendarProvider` (Rust, `src-tauri/src/calendars`) et un **simulateur Google local** (`tests/sim/google-sim.mjs`, serveur HTTP) qui reproduit autorisation, jeton, rafraîchissement, révocation, `calendarList`, `events.list` (instances de séries, journées entières, annulés) et les erreurs 401, 403, 410, 429, 5xx. L'URL de base et l'ID client sont configurables ; les tests vitest, cargo test et Playwright visent le simulateur. Sont donc faisables : flux OAuth PKCE (boucle locale 127.0.0.1 sur PC), stockage du jeton (coffre simulé en test), écrans Réglages › Agendas, choix des agendas et espace (ES-06), conversion en `external_event`, alerte « Reconnecter » (A-09).

## Critères testables

1. **Étant donné** Réglages › « Agendas · Rappels Apple », **alors** l'écran « Agendas » liste les comptes (valeur de la ligne : « Aucun compte » / « 2 agendas ») et le bouton « Ajouter un compte » propose Google (et iCloud, K-02).
2. **Quand** je choisis Google, **alors** le navigateur système s'ouvre sur la page de consentement (PC : redirection 127.0.0.1 avec PKCE et `state` vérifié ; iPhone : session d'authentification web) ; un refus ou une fermeture annule sans rien enregistrer et affiche « Connexion annulée ».
3. **Quand** l'autorisation réussit, **alors** un `calendar_account` (provider google, label = adresse Google) est créé ; les jetons vont dans le coffre système (`token_ref` seul en base) ; aucun jeton dans la base, les journaux ni l'état de l'interface.
4. **Alors** la liste des agendas Google s'affiche avec, pour chacun : case « Afficher », nom, couleur, et sélecteur Pro / Perso (ES-06 critère 5, prérempli Pro) ; un agenda affiché sans espace est refusé.
5. **Quand** je change l'espace d'un agenda, **alors** ses événements suivent immédiatement le filtre, sans nouvelle synchro (ES-06 critère 6) ; décocher « Afficher » retire ses événements de toutes les vues sauf liste des agendas.
6. **Quand** j'enregistre, **alors** un premier rafraîchissement (K-03) charge les événements : titres, début et fin en UTC, journée entière (fin exclue), séries déjà développées en instances ; ils apparaissent dans la Semaine et Aujourd'hui (S-05 critère 10).
7. **Étant donné** un jeton refusé (401) ou révoqué, **alors** le compte passe « Déconnecté », le cadre d'état affiche « Agenda <nom> déconnecté » + « Reconnecter » (A-09 critère 10) qui relance le flux ; les événements déjà chargés restent visibles, estampillés.
8. **Quand** je supprime un compte (confirmation), **alors** le jeton est effacé du coffre et révoqué si possible, ses `external_event` sont supprimés, les tâches liées (K-04) gardent titre et date.
9. **Alors** la portée demandée est `calendar.readonly` seule ; aucune écriture vers Google ; l'ID client n'est jamais affiché.
10. **Étant donné** les vrais comptes d'Ali, **alors** parcours clé 8 vérifié à la main (attend Ali).

## Hors de cette story

- Rafraîchissement périodique : K-03 ; Apple : K-02 ; tâche liée : K-04 ; Rappels Apple : K-05 (ordre 5) ; édition des événements Google.

## Décisions (validation automatique)

- D1 — Un jeton par appareil : `token_ref` est local ; `calendar_account` (label, agendas, espaces) se synchronise. Sur un autre appareil sans jeton, le compte apparaît « Déconnecté » avec « Reconnecter » (cohérent avec A-09).
- D2 — iPhone : petit plugin Swift d'authentification web (ASWebAuthenticationSession) à ajouter à la liste des plugins ; non testable sans iPhone (build CI + vérification d'Ali). À faire valider par l'architecte (ADR).
- D3 — Fenêtre chargée : 60 jours avant à 400 jours après aujourd'hui.
- D4 — Valeur de la ligne de Réglages : « Aucun compte » / « N agendas » (les listes Rappels s'y ajoutent avec K-05).
- D5 — Écran « Agendas » non dessiné : mêmes codes que « Silence Pro » (ES-07).

## Ordre des sous-tâches

1. architect : contrat `CalendarProvider`, coffre (`keyring`), plugin Swift d'authentification, ADR.
2. data-model : écritures `external_event` (upsert par compte, agenda, identifiant) et `calendar_account` ; test sur base peuplée.
3. domain-logic : conversion Google → `external_event` (UTC, journée entière, annulés).
4. Rust : flux OAuth PKCE, client Google, simulateur `tests/sim/google-sim.mjs` ; cargo test.
5. UI : écran Agendas, choix des agendas et espaces, alerte « Reconnecter ».
6. Tests e2e sur simulateur ; qa-test, code-reviewer ; vérification réelle par Ali.

## Réalisation (calendar-integration, ordre 2)

Statut : critères 1 à 9 verts sur simulateur (Vitest, cargo test, Playwright `pc` et `iphone`) ; critère 10 et vérification iPhone attendent Ali.

- Rust (`src-tauri/src/calendars`) : coffre système (`keyring` 3), `calendar_http` limité aux hôtes de l'ADR 0008 (redirections contrôlées, `Authorization` refusé), OAuth PKCE S256 + `state` sur 127.0.0.1 (délai 5 min), rafraîchissement du jeton (échéance ou 401, une fois), révocation. Aucune commande ne rend un secret. iPhone : `calendar_oauth_google_authorize` rejette `unsupported` (plugin Swift `web-auth` à l'ordre 5, ADR 0008 section 5).
- TypeScript : `providers/google.ts` (analyse JSON de `calendarList` et `events.list`), `calendarsStore.ts` (comptes, états locaux, A-09), `refreshUseCase.ts` (lecture de la fenêtre puis écriture en UNE transaction), écran `CalendarsScreen` (Réglages › Agendas).
- Écart avec la fiche : l'écran Agendas enregistre chaque changement aussitôt (case « Afficher », espace Pro / Perso), sans bouton « Enregistrer » : c'est la lecture littérale d'ES-06 critère 6 (« immédiatement »). Les agendas sont tous affichés à la connexion, rattachés à Pro (ES-06 critère 5) ; la pastille de couleur d'un agenda est celle de son espace.

### Ce qu'Ali doit fournir, et où

Rien n'est commité. Les identifiants client OAuth se lisent à la compilation, dans cet ordre : variable d'environnement du build, puis fichier `.env` à la racine du dépôt (ignoré par git).

| Variable | Contenu | Où |
| --- | --- | --- |
| `CT_GOOGLE_CLIENT_ID` | ID client OAuth Google de type « Application de bureau » (PC) | `.env` local : `CT_GOOGLE_CLIENT_ID=123456789-xxxx.apps.googleusercontent.com`, ou variable d'environnement avant `npm run tauri build` |
| `CT_GOOGLE_CLIENT_SECRET` | seulement si Google refuse l'échange sans secret pour ce client de bureau (Google le déclare non confidentiel) | idem, jamais commité |
| `CT_GOOGLE_IOS_CLIENT_ID` | ID client de type « iOS » (iPhone, ordre 5) | secret GitHub pour `build-ios.yml` (à brancher avec le plugin `web-auth`) |

Sans `CT_GOOGLE_CLIENT_ID`, le bouton « Google » affiche « Google n'est pas configuré dans cette version de l'application » (code `config-missing`) : rien n'est enregistré. Après modification de `.env`, relancer `npm run tauri dev` (le script de compilation relit le fichier).

Côté Google Cloud : API Google Calendar activée ; écran de consentement « Externe » avec Ali comme utilisateur, passé en Production (en mode Test, le jeton de rafraîchissement expire après 7 jours) ; portée `https://www.googleapis.com/auth/calendar.readonly` seule ; URI de redirection : le client « Application de bureau » accepte `http://127.0.0.1:<port>` sans déclaration.

Vérification réelle (parcours clé 8) : connexion, agendas listés, événement visible dans la Semaine, jeton révoqué depuis myaccount.google.com › Sécurité › Accès de tiers → « Agenda … déconnecté » + « Reconnecter ».
