## État des lieux (relu le 2026-10-08)

- Le seul point d'écriture du journal est `logFailure(scope, detail)` (`src/platform/desktop/log.ts`, 76 appels dans 28 fichiers, journal du synchro `src/sync/log.ts` compris) : `console.warn` seulement, **rien n'est conservé** ; sur iPhone sans Safari, il est illisible. Trois `eprintln!` en Rust (`backup.rs`, `desktop.rs`, `sync/mod.rs`) ont le même défaut. Les décisions P-04 du 2026-10-05 renvoient à cet écran : « l'écran de logs de M12 lira le journal ».
- Constat à corriger au passage (règle d'Ali) : `restore_backup` n'écrit le marqueur de restauration qu'avec un `eprintln!` si l'écriture échoue : la restauration réussit, la synchro n'est pas suspendue, l'utilisateur ne le sait pas (traité dans P-04-iOS, critère 12).
- La base ne convient pas pour stocker le journal : une restauration (P-04) remplace la base et effacerait les logs qui l'expliquent ; une table touche `src/db` (interdit dans ce lot) et se synchroniserait par erreur.

## ADR requis avant le code

**ADR 0014 « Journal technique persistant » par l'architecte, avant la première ligne.** Contenu attendu :
1. Stockage : fichier du dossier de configuration de l'app (`logs/circletasks.log` et `.1`, 256 Kio chacun, rotation à l'écriture, `.tmp` inutile : ajout en fin), jamais dans le dossier iCloud, jamais dans `backups/`, jamais synchronisé ; commandes Rust `log_append(lines)` (lot de 100 lignes, 4 Kio au plus par ligne, hors fil de l'interface), `log_read(max)` (500 dernières entrées), `log_clear` ; capability `logs.json` (PC, `main`) et `logs-ios.json` (iPhone, `main`), listes exactes testées ; les eprintln! Rust passent par la même fonction `applog::write(scope, code)`.
2. Format d'une entrée : `{ at ISO UTC, scope, code, detail }`, catégorie déduite du `scope` (`sync*` = Synchro, `notifications` / `reminders` = Notifications, le reste = Erreurs) ; **assainissement** obligatoire avant écriture (`sanitizeLogDetail`, dans `src/platform/logs`, pas dans `src/domain`) : chemins (`C:\…`, `/var/…`, `file://`), URL avec requête, adresses e-mail, jetons, chaînes de plus de 300 caractères, titres : remplacés par `[masqué]` ; règle écrite : un appelant ne passe que des codes, compteurs et identifiants techniques.
3. Intégration : `logFailure` devient le seul entonnoir (mémoire tampon de 500 entrées + vidage toutes les 2 s et au passage en arrière-plan) ; l'échec d'écriture du journal est lui-même visible (critère 10) et le tampon de la session reste lisible ; limites assumées : les plantages natifs (Swift, WebKit) ne sont pas capturés ; la mini-fenêtre PC (`captureMain`) écrit dans la console seulement tant qu'elle n'a pas la capability.

## Critères testables sans Mac

Légende : **[R]** cargo test, **[U]** Vitest, **[S]** contrôle statique, **[E]** Playwright (projets `iphone` et `pc`), **[CI]** `build-ios.yml`.

1. **[U]** **Étant donné** Réglages › À PROPOS, **alors** la ligne « Version … » porte le lien « Logs » (iPhone **et** PC : le code est partagé) ; il ouvre l'écran de logs (titre `h1` focalisé, retour).
2. **[U]** **Étant donné** des entrées de scopes `sync`, `notifications` et `backup`, **alors** l'écran les liste de la plus récente à la plus ancienne (heure locale 24 h, scope, code), avec les filtres « Tout », « Synchro », « Notifications », « Erreurs » ; chaque filtre est testé ; un journal vide affiche « Aucune entrée » (pas d'écran blanc).
3. **[U]** **Étant donné** `logFailure('sync', …)` appelé, **alors** l'entrée est dans le tampon, vidée vers `log_append` dans les 2 s, relue par `log_read` après redémarrage simulé (faux transport) : **le journal survit à la fermeture et à une restauration de la base**.
4. **[R]** **Alors** rotation : au-delà de 256 Kio le fichier devient `.1` (l'ancien `.1` est remplacé), jamais plus de 512 Kio au total ; une ligne de plus de 4 Kio est tronquée avec marque ; `log_clear` supprime les deux fichiers ; un fichier du dossier qui est un lien symbolique n'est ni lu ni écrit ; un fichier illisible rend `unreadable` sans planter (test sur fichier corrompu en UTF-8 : lecture avec remplacement, entrée marquée).
5. **[U]** **Alors** `sanitizeLogDetail` masque chemin Windows, chemin POSIX, `file://`, URL avec requête, e-mail, `Bearer …`, séquence hexadécimale de 32 caractères ou plus, chaîne de plus de 300 caractères ; jeu de 40 entrées réelles tirées des 76 appels existants : aucune ne contient de titre ni de chemin après assainissement.
6. **[U]** **Alors** un test d'intégration déclenche un parcours complet avec des **titres de tâches sentinelles** (« TITRE-SECRET-123 ») : synchro, rappels, import CSV, sauvegarde, restauration, scan, dictée ; le journal, son export et le tampon **ne contiennent jamais** la sentinelle (même technique que l'audit B6 de la synchro).
7. **[U]** **Quand** je touche « Exporter », **alors** `files.save` reçoit un texte UTF-8 `circletasks-logs-AAAAMMJJ-HHMM.txt` (`text/plain`) : en-tête (application, version, système, version de schéma, date, nombre d'entrées, mention « Ce fichier ne contient ni titres ni notes »), puis une ligne par entrée `AAAA-MM-JJ HH:MM:SS scope code détail`, heures UTC avec le décalage indiqué en en-tête ; annulation = rien, pas d'erreur ; échec d'enregistrement = message visible « L'export n'a pas abouti » avec le code (`FileExportError`).
8. **[U]** **Quand** je touche « Effacer », **alors** une confirmation (« Annuler » par défaut) précède la suppression ; après confirmation le journal est vide et une entrée `logs-cleared` est la première du nouveau journal.
9. **[S]** **Alors** un test parcourt `src` et `src-tauri/src` : aucun `console.warn|error|log` hors `src/platform/desktop/log.ts`, aucun `eprintln!` hors `applog`, aucun appel de `log_append` hors `src/platform/logs` (seul fichier à nommer les commandes) ; capabilities `logs*.json` exactes ; aucune capability de `pairing`, `capture` ni `focus` ne porte les commandes.
10. **Aucun échec silencieux.** **Étant donné** que `log_append` échoue (disque plein, dossier illisible), **alors** l'écran de logs et la ligne « Logs » de Réglages affichent « Le journal n'a pas pu être écrit » avec le code, en rouge #9E3F33 ; les entrées de la session restent lisibles en mémoire ; le message disparaît à la prochaine écriture réussie ; l'échec de **lecture** (`unreadable`) s'affiche de même au lieu d'une liste vide.
11. **[E]** Projet `iphone` : ouvrir Réglages › Logs avec un faux journal de 600 entrées (500 affichées au plus, défilement), filtrer, exporter (faux `FileService` : contenu vérifié, aucune sentinelle) ; projet `pc` : même parcours.
12. **[U]** **Alors** accessibilité : filtres en `aria-pressed`, liste en `role="log"` non annoncée en continu, boutons ≥ 44 pt, texte jusqu'à 200 %, contraste AA clair et sombre.
13. **[CI]** `build-ios.yml` vert sur la branche du lot ; contrat Info.plist inchangé ; capability `logs-ios.json` exacte (`config.rs`).

## Critères seulement vérifiables sur l'appareil (reportés dans `_checklist-ordre-5.md`)

- A1. Provoquer une erreur visible (Rappels refusés, dossier iCloud inaccessible) : l'entrée apparaît dans Logs avec l'heure locale correcte ; fermer l'app de force, rouvrir : l'entrée est toujours là.
- A2. « Exporter » : la feuille de partage d'iOS s'ouvre ; envoyer le fichier par Mail ou AirDrop au PC, l'ouvrir : lisible (UTF-8, accents), en-tête exact, **aucun titre de tâche** après une journée d'usage normal.
- A3. Journal et verrou Face ID : écran de logs accessible seulement déverrouillé (il est dans l'interface) ; aucune entrée ne contient de contenu.
- A4. Restaurer une sauvegarde (P-04-iOS) : les logs d'avant la restauration sont toujours là ; l'entrée `restore-done` figure au journal.
- A5. Journal plein (plus de 500 Kio d'usage, simulé) : rotation sans ralentissement visible de l'ouverture de l'écran.

## Hors de cette story

Envoi automatique des logs, service de télémétrie ou de plantages (hors périmètre : vie privée), niveaux de verbosité réglables, capture des plantages natifs, recherche plein texte dans les logs, journal de la mini-fenêtre PC.
