## Contexte

- Constat (audit 1.0, B6) : quand un appel au dossier iCloud ne répond jamais (réseau coupé pendant une coordination de fichier, fichier évincé en cours de téléchargement hors ligne, `NSFileCoordinator` bloqué par un autre processus), la synchro de l'iPhone reste sur « Synchro en cours » jusqu'à la relance de l'app. Aucune erreur, aucun état d'attente : c'est un échec silencieux au sens de la règle d'Ali.
- Causes vérifiées à la rédaction (worktree `y-ios-05`, `main` c01e961b, 2026-10-18). Les adresses de l'audit correspondent encore au code ; les lignes actuelles sont celles-ci :
  - `src-tauri/plugins/folder-bookmark/src/lib.rs:41` : `self.handle.run_mobile_plugin::<Value>(command, args)` attend la réponse sans délai (`rx.recv()` de Tauri). Seuls Vision, Speech et ct-files passent par `crate::mobile_call::call_with_deadline` (`src-tauri/src/mobile_call.rs:25`, utilisé par `ocr/vision.rs:105,167,177`, `speech/mod.rs:176-272`, `export_ios.rs:224`). Le plugin folder-bookmark n'y passe pas : `sync/bookmark.rs:454-457` (`PluginTransport::call`) appelle directement `FolderBookmark::call`.
  - `src-tauri/src/sync/service.rs:841-866` (`scan_inner`) : le verrou `inner` (`self.lock()`, ligne 842) est tenu pendant tout le scan, y compris pendant `store.scan_within(...)` (ligne 865) qui traverse le transport. Un appel muet garde donc le verrou, et toute autre commande de synchro qui le demande attend derrière lui.
  - `FolderBookmarkPlugin.swift:409-424` (`coordinatedRead`) et les trois autres coordinations (`coordinatedWrite` 427, `coordinatedDelete` 446, `coordinatedMove` 463) : `NSFileCoordinator.coordinate(...)` bloque sans limite tant que le fichier n'est pas disponible ; aucune annulation (`cancel()` n'est appelé nulle part).
  - `FolderBookmarkPlugin.swift:119` : `fileQueue` est une file **série** (`DispatchQueue(label:)` sans attribut concurrent) et `onFiles` (219-230) y exécute tous les travaux : une coordination bloquée **bloque tous les appels suivants**, même ceux qui n'auraient pas besoin d'iCloud.
  - `FolderBookmarkPlugin.swift:388-406` (`availability`) rend `"error"` quand `resourceValues` échoue (ligne 397). Conséquences : (1) `readFrom` (758-833) ne refuse que `availability == "cloud"` (ligne 773) ; un état illisible passe donc à `coordinatedRead(..., metadataOnly: false)` (ligne 776), qui attend un téléchargement hors ligne : c'est le blocage décrit par l'audit ; (2) côté Rust, `bookmark.rs:84-90` et `bookmark.rs:241` traduisent `"error"` en `Availability::Error` puis `FsError::Unsafe` (`unsafe-folder`), une panne **durable** là où la cause est transitoire.
  - `FolderBookmarkPlugin.swift:835-887` (`download`) : `try? item.resourceValues(...)` (ligne 850) donne `nil` si l'état est illisible, puis la ligne 858 (`values?.isUbiquitousItem != true`) rend `[:]` : l'échec est avalé, « rien à télécharger », et la lecture coordonnée qui suit attend le téléchargement.
- Pourquoi aucun test ne l'attrapait : le faux transport de Windows (`fake_bookmark.rs`, `MemFs`) répond toujours et refuse l'effet `mute` à l'armement (ADR 0011 §25 point 2 : « l'échéance par appel du Rust de production est l'objet de Y-IOS-05, qui définira avec elle la forme du faux ») ; `memory.ts` le rejoue mais sans échéance, par une promesse jamais résolue tant que le test ne la libère pas ; et aucune ligne Swift n'est jamais exécutée (pas de Mac, ADR 0011 §25 point 6).
- Preuve rouge déjà écrite : `tests/unit/sync/hostile/scenario5MuteTransport.test.ts`, sur `origin/y-tech-03-scenarios-rouges` (règle de Y-TECH-03 critère 24 : livré sur la branche du correctif, pas sur celle du banc). Plan `scenario-5-transport-muet` de `tests/fixtures/sync/fault-plan.json` (lignes 109-111) : listage `devices/56d4eec1-aaaa-4aaa-8aaa-aaaaaaaaaaaa/` au rang 1 en `mute`.

## Décisions retenues

1. **L'échéance vit à trois endroits qui disent la même chose.** (a) **Rust, couche transport** : un décorateur `DeadlineTransport` (dans `src-tauri/src/sync/bookmark.rs`, compilé sous la même condition que `BookmarkFs`) entoure tout `Arc<dyn BookmarkTransport>` et appelle `call_with_deadline` (déjà écrit, testé, en production pour Vision et Speech). Il se place dans `commands_ios.rs` (`plugin_transport`, lignes 56-59), donc **sous** `BookmarkFs`, `BookmarkBackend`, `IosConsentUi` : un seul point, tous les appels du plugin sont couverts. `lib.rs:41` ne change pas (le crate du plugin ne peut pas dépendre de `mobile_call` de l'app, et reste la primitive bloquante) ; l'agent vérifie par recherche qu'aucun autre appelant de `FolderBookmark::call` ne contourne le décorateur. (b) **Swift, garde de coordination** (décision 4) : première ligne de défense, qui rend la file libre. (c) **TypeScript, `memory.ts`** : le faux modélise l'échéance pour que le scénario 5 du banc puisse passer ; c'est une modélisation, pas du code de production.
2. **Valeurs.** Appel de fichier (`resolve`, `status`, `list`, `readFrom`, `append`, `writeAtomic`, `rename`, `createDir`, `remove`, `removeEmptyDir`, `appState`) : **20 s**. `download` : `timeoutMs` de l'appel + **5 s** (le plugin rend `cloud-pending` à `timeoutMs`, Rust n'est que la seconde ligne). `pickFolder` et `confirm` (interaction de l'utilisateur, durée sans borne) : **exclus**, appelés directement comme aujourd'hui. Cohérence avec l'arrière-plan : le moteur borne déjà son cycle à 25 s (ADR 0011 §22 point 6) et la tâche d'arrière-plan Swift à 28 s (`backgroundGuardSeconds`, ligne 129) ; 20 s tient dedans. Constantes nommées dans `src-tauri/src/sync/limits.rs`, injectables (`DeadlineTransport::with_limits`) pour les tests.
3. **Sortie d'échéance : `cloud-pending`, jamais un nouveau code.** `CallError::Timeout` devient le code `cloud-pending` (déjà dans `PLUGIN_REJECT_CODES`, `fs_error_of` → `FsError::CloudPending`). Le moteur le range déjà en « attente d'iCloud » (`status.ts:31`, `WAITING_CODES`), famille `transient` (`errorFamily.ts:24`). Le journal technique reçoit l'événement `bookmark-call-timeout` avec **le seul nom de la commande** (jamais de chemin, d'argument, ni de texte).
4. **Que devient l'appel abandonné.**
   - **Côté Swift (cause)** : chaque coordination (`coordinatedRead`, `Write`, `Delete`, `Move`) arme une garde de **15 s** (`coordinationGuardSeconds`, plus courte que les 20 s de Rust : Swift répond d'abord et proprement). La garde est un `DispatchWorkItem` sur une file globale qui appelle `coordinator.cancel()` et lève un drapeau protégé par un verrou ; elle est annulée dès le retour de `coordinate`. Au retour : si le corps a produit un résultat, il est rendu tel quel (une annulation ne défait pas un corps déjà commencé) ; sinon, si le drapeau est levé, `Failure(code: .cloudPending)` ; sinon (erreur de coordination sans garde) `io`, comme aujourd'hui. La garde **n'appelle jamais `invoke`** : la réponse reste unique, celle de `onFiles` (garde contre un double achèvement). La file série est donc libérée : l'appel suivant n'est plus bloqué par le précédent.
   - **Côté Rust (filet)** : `call_with_deadline` laisse son fil dédié bloqué jusqu'à la réponse de Swift (`mobile_call.rs:5-6`) ; la réponse tardive est jetée (`mobile_call.rs:31`, `let _ = sender.send(...)`). Pour que des appels muets ne s'empilent pas en fils, le décorateur tient un compteur d'appels abandonnés (au plus **1**) : tant qu'un appel abandonné n'a pas répondu, toute nouvelle commande non exclue répond `cloud-pending` **aussitôt, sans être envoyée** (la file série de Swift la ferait attendre derrière l'appel bloqué de toute façon). Le compteur redescend quand l'appel abandonné rend enfin la main.
   - **Verrou `inner`** : il n'est plus tenu au-delà de l'échéance, puisque `scan_inner` retourne l'erreur `cloud-pending` comme n'importe quelle autre ; aucune modification de `service.rs`.
5. **`"error"` renvoyé par Swift pour un état illisible est traité comme `cloud`** (transitoire), avec une précision par rapport à la lettre de l'audit. `"error"` a deux sources : un **état de téléchargement illisible** (`availability`, ligne 397) et un **lien symbolique** (lignes 677 et 740, jamais suivi, panne durable légitime `unsafe-folder`). Seul le premier devient `"cloud"` : `availability()` rend `"cloud"` quand `resourceValues` échoue ; `readFrom` refuse tout état autre que `local` avec `cloud-pending` avant toute coordination ; `download` sur un état illisible lève `cloud-pending` au lieu de rendre `[:]`. Le lien reste `"error"` → `unsafe-folder` côté Rust (comportement figé par les cas de conformité existants). Aucun changement du contrat JSON (mêmes trois valeurs).
6. **Ce que voit Ali.** Aucun texte nouveau. Un appel muet donne `errorCode: cloud-pending`, phase `waiting-icloud` : libellé « En attente d’iCloud » (`fr.syncEngine.ts:21`) et, dans Détails, « iCloud ne répond pas : vos modifications seront envoyées au retour » (`fr.syncEngine.ts:43`, `errorCloud`). Cela devient **durable** par les mécanismes existants, sans nouveau code : après `SLOW_AFTER = 3` échecs de suite avec le même code, `errorStreak` monte et `retryAt` espace les essais de `SLOW_RETRY_MS` (jamais un arrêt) ; au-delà de 24 h d'attente, `waitingSince` fait afficher « Synchro incomplète depuis plus de 24 h, en attente d’iCloud : vérifiez qu’iCloud Drive est activé dans Réglages… » (`waitingIcloudLongIos`, ligne 24). Rien n'est silencieux.
7. **Le faux TypeScript compte l'échéance, ne la chronomètre pas.** Commentaire du scénario 5 : « Le correctif devra COMPTER l'échéance de l'appel (rang, tours, cycles du faux), jamais la chronométrer : aucun setTimeout ni horloge réelle dans memory.ts ni dans ce test. » `MemorySyncFolder.suspend` (memory.ts:452) lance, en plus de la mise en attente, un compteur de **`MUTE_DEADLINE_TURNS = 100` tours de micro-tâche** (`await Promise.resolve()` en boucle) ; à l'échéance, si l'appel est encore dans `muted`, il est retiré et rejeté avec `SyncPlatformError('cloud-pending')`, exactement la réponse d'un transport borné (déjà documentée sur `releaseMuted`, memory.ts:463-466). Borne imposée par les tests existants et par le scénario : strictement entre **50** (`memoryFaults.test.ts:265` attend 50 tours avec l'appel encore en suspens) et **500** (`CALL_DEADLINE_TURNS` du scénario, qui doit laisser au cycle le temps de se terminer après l'échéance) ; 100 laisse 400 tours au moteur. Aucun champ ajouté au format du plan de pannes (donc ni lecteur Rust à modifier, ni table de refus).
8. **Forme du faux Rust** (ADR 0011 §25 point 2 réservait la décision). L'effet `mute` **reste refusé** par `MemFs` et `fake_bookmark` (un appel synchrone sans retour ne se rejoue pas sans attente). Le test Rust utilise un **transport muet dédié**, `MutedTransport` (un `BookmarkTransport` qui, pour une commande désignée, bloque sur un canal jusqu'à ce que le test l'y libère, et répond sinon comme `fake_bookmark`), défini dans `src-tauri/tests/desktop/sync_bookmark.rs`. Il est inscrit, avec sa raison, dans la table d'exemptions de `tests/unit/sync/hostile/fakesLoadFixtures.test.ts` (ligne 43, comme `Never`), car la règle « tout faux iCloud rejoue les deux fixtures » (ADR §25 point 5) fait échouer tout `impl BookmarkTransport` non déclaré. **Aucun délai réel dans les tests Rust** : les tests de l'échéance injectent `Duration::ZERO` (un appel muet n'envoie jamais de réponse, donc `recv_timeout(0)` rend `Timeout` de façon déterministe) ; les tests de transmission utilisent une échéance large sur un transport qui répond aussitôt. Aucune assertion ne dépend d'une durée mesurée.
9. **Bundle de départ saturé** (358 357 octets gzip pour 358 400, **marge de 43 octets**). Côté TypeScript, seul `memory.ts` bouge : net ≤ 0 octet sur le départ, ou la logique d'échéance rangée dans du code déjà chargé à la demande ; mesure de `tests/bundle/startBundle.test.ts` après chaque commit TypeScript ; **arrêt et question à Ali si la marge ne suffit pas** (les paliers sont sa décision, mémoire projet « Bundle de départ saturé »). Côté Rust et Swift : aucune contrainte de bundle.
10. **Parallélisme avec Y-FIX-02 : oui, sous une condition de contrôle.** Fichiers de Y-IOS-05 : `src/platform/sync/memory.ts`, `src/platform/sync/memoryFaults.test.ts`, `tests/unit/sync/hostile/scenario5MuteTransport.test.ts` (nouveau), `tests/unit/sync/hostile/fakesLoadFixtures.test.ts` (une ligne), `src-tauri/src/sync/bookmark.rs`, `src-tauri/src/sync/commands_ios.rs`, `src-tauri/src/sync/limits.rs`, `src-tauri/tests/desktop/sync_bookmark.rs`, `src-tauri/plugins/folder-bookmark/ios/Sources/FolderBookmarkPlugin.swift`, et docs. Y-FIX-02 touche `engine.ts`, `publisher.ts`, `epoch.ts` : **aucun recoupement de source**. Recoupement possible seulement sur `memory.ts` et `tests/fixtures/sync/fault-plan.json` si Y-FIX-02 étend le banc (par exemple un point de panne pour l'arrêt brutal) : l'agent compare `git diff --name-only main...origin/<branche Y-FIX-02>` au démarrage et avant le push, et rebase explicitement s'il y a recoupement. `store.rs` n'est **pas** touché (la fiche Y-IOS-07 le dit partagé « pour le seul appel de lecture » : à corriger, voir « Écarts signalés »), donc aucun conflit avec Y-IOS-07 non plus.
11. **Preuve : ce qui est prouvé, ce qui ne l'est pas.** Prouvés en CI : le scénario 5 du banc (le moteur sort de l'attente par `cloud-pending`), le décorateur Rust contre un transport muet (échéance, verrou libéré, compteur d'abandon, exclusions), les contrôles statiques du Swift (garde, `cancel()`, réponse unique, `"error"`/`cloud`). **Non prouvé** : le comportement réel de `NSFileCoordinator.cancel()` et d'iCloud (Swift jamais exécuté avant la compilation `build-ios.yml` et l'iPhone). ## Limites assumées

- Le banc ne prouve pas le comportement réel d'iOS : ni que `NSFileCoordinator.cancel()` débloque un `coordinate` en attente d'un téléchargement hors ligne, ni le moment où iOS lève l'attente. Les contrôles Swift sont **statiques** ; le comportement est observé à la séance iPhone.
- `cancel()` n'a aucun effet sur un corps de coordination déjà commencé : la garde protège l'attente de la coordination, pas une lecture locale déjà en cours (courte et locale par construction).
- Le fil Rust d'un appel abandonné reste bloqué jusqu'à la réponse de Swift (`mobile_call.rs`), au plus un à la fois grâce au compteur. Un plugin Swift définitivement mort ferait répondre `cloud-pending` à chaque cycle (visible, espacé par `retryAt`) jusqu'au redémarrage de l'app.
- La seconde ligne (Rust, 20 s) et le faux TypeScript (100 tours) ne sont pas la même mécanique : le banc TypeScript prouve la **tenue du moteur** face à `cloud-pending`, pas le décorateur Rust, qui a ses propres tests (critères 7 à 14).
- Le rouge du critère 14 est le rouge du câblage ; les tests de comportement du décorateur (critères 7 à 13) échouent d'abord par non-compilation (le type n'existe pas) : ils ne comptent pas comme preuve rouge, qui reste le scénario 5 et le contrôle de câblage.

## Questions à Ali (sans bloquer le développement ; recommandations)

1. **Valeurs de l'échéance : 20 s (fichier), `timeoutMs` + 5 s (téléchargement), garde Swift 15 s.** Recommandation : les retenir. 20 s tient dans le cycle de 25 s de l'arrière-plan ; plus court ferait échouer des listages lents mais sains sur une mauvaise connexion, plus long dépasserait la tâche d'arrière-plan. Réglable à la vérification manuelle.
2. **`"error"` : seul l'état illisible devient transitoire, le lien symbolique reste une panne durable.** Recommandation : oui. Traiter aussi le lien comme `cloud` ferait attendre iCloud pour toujours un dossier piégé, ce qui est exactement un échec silencieux.
3. **Un seul appel abandonné toléré, puis réponse immédiate `cloud-pending` sans envoi.** Recommandation : oui. La file de Swift étant série, un second appel attendrait derrière le premier de toute façon ; sans compteur, un iPhone bloqué accumulerait un fil par cycle.
4. **Test de l'échéance Rust à `Duration::ZERO`, sans attente réelle.** Recommandation : oui. Un appel muet ne répond jamais, donc le résultat est déterministe et le test ne dure pas plus qu'un autre ; c'est l'application de « aucun délai réel dans les tests » à un code dont l'objet est une échéance.
5. **Bundle : marge de 43 octets.** Si la logique d'échéance de `memory.ts` fait dépasser le départ, l'agent s'arrête et vous demande le levier (rangement à la demande ou palier), sans rien décider seul. Recommandation : accepter le rangement à la demande en premier, avant tout relèvement de palier.
