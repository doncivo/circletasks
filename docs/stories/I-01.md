| ID | User story | Critères d'acceptation |

| I-01 | J'installe l'app sur l'iPhone | Installation SideStore guidée, source CircleTasks, IPA construite sans Mac |

Le lot I0 ajoute à la story la chaîne CI par branche (chaque lot à plugin Swift est accepté seulement si `build-ios.yml` lancé sur sa branche est vert) et le contrat des permissions Info.plist. Références : ADR 0007 et ses avenants, `docs/install-iphone.md`.

## Critères testables (vérifiables sans Mac)

1. **Étant donné** une branche de lot, **quand** `gh workflow run build-ios.yml --ref <branche> -f publish=false` est lancé, **alors** l'IPA est produite et les contrôles existants passent (bundle `fr.circletasks.planner`, iOS 18, arm64, front embarqué), sans aucune publication. Jamais de publication hors tag `ios-v*` et approbation de l'environnement `releases`, même avec `publish` coché sur une branche.
2. **Étant donné** `scripts/ios/plist-contract.json` qui liste les clés exigées par plugin (vide au départ), **quand** le build tourne, **alors** une étape lit le Info.plist de l'IPA et échoue si une clé listée manque ou si une description d'usage est vide. Le format permet à chaque lot de plugin d'ajouter ses clés (caméra, micro, reconnaissance vocale, rappels, Face ID ; les notifications n'ont pas de clé). Test unitaire du script de contrôle.
3. **Étant donné** `make-source-json.mjs`, **quand** un test le lance, **alors** le JSON a les champs attendus par SideStore (version, date, URL de téléchargement, taille, iOS minimum, notes) et une nouvelle version s'ajoute sans écraser les précédentes.
4. **Étant donné** `docs/install-iphone.md`, **quand** un test de cohérence le lit, **alors** l'URL de la source, le nom de l'app, l'identifiant du bundle et le tag `ios-v` sont identiques à ceux du workflow et du script. La phrase « préviendra 24 h avant l'expiration (à l'ordre 5) » reste jusqu'à I-02.
5. Le guide tient en 15 minutes au plus de lecture et d'action.

## Sur l'appareil (Ali, en fin d'ordre)

Inscrit dans `docs/stories/_checklist-ordre-5.md` : installation SideStore en moins de 15 minutes, lancement après approbation du profil, données conservées après une mise à jour.

## Réalisation

- `.github/workflows/build-ios.yml` : job `publish` conditionné au tag `ios-v*` (push du tag, ou lancement manuel sur le tag avec `publish`) et seconde barrière dans le script de publication ; étape « Contrat des permissions Info.plist » (`plutil -convert xml1`, puis `check-plist-contract.mjs`) ; résumé du run (taille, SHA-256, version, descriptions d'usage) ; artefact `CircleTasks-info-plist` lu par la publication.
- `scripts/ios/plist.mjs` (lecture d'un plist XML), `scripts/ios/check-plist-contract.mjs`, `scripts/ios/plist-contract.json`.
- `scripts/ios/make-source-json.mjs` : options nommées, contrôles du Info.plist de l'IPA (version, bundle, iOS minimum), `iconURL` (obligatoire pour SideStore, absent de la source publiée en 0.1.0), `buildVersion`, `sha256`, `appPermissions` informatif, champs d'app hérités, iOS minimum lu dans `tauri.conf.json`, toutes les versions conservées.
- Tests : `scripts/ios/ios.test.ts` (projet Vitest `node`).

## Écarts et points à arbitrer

- La source publiée (0.1.0) n'a pas d'`iconURL` ; le code de SideStore (`StoreApp.swift`, branche develop) l'exige : la source actuelle est probablement refusée. Corrigé à la prochaine publication (`ios-v*`), l'icône `icon.png` étant copiée dans circletasks-releases.
- L'environnement GitHub `releases` n'a qu'une règle de branches (main, `ios-v*`, `v*`) et aucun « Required reviewers » : l'approbation d'Ali n'est pas exigée aujourd'hui (réglage du compte GitHub, à faire par Ali).
