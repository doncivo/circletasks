# Y-08 — Mes données dans iCloud sont chiffrées

Module : M15 Synchronisation · Ordre de construction : 4 (lot Y1, première story du lot) · Agent : **sync-icloud** (Rust : `src-tauri/src/sync/`, `vault.rs`, capabilities) · Relectures : qa-test, code-reviewer, **security-privacy** (obligatoire : coffre, confirmation native, fenêtre `pairing`) · Statut : en revue (« fait » après le parcours 11, D2)
Plateforme : PC (Windows) à l'ordre 4 ; l'iPhone (Trousseau, scan du QR) est un contrat compilé par la CI, vérifié à l'ordre 5.
Dépend de : l'amorce (commit 2092549 : `src/domain/sync/{format,limits}.ts`, `src/platform/sync/{types,memory}.ts`), `src-tauri/src/calendars/vault.rs` (déplacé), D-01 (fenêtre `main`, capabilities), Q-01 (précédent de la fenêtre dédiée `capture`).
Précède : Y-01 (même lot, qui appelle `sync_key_create` au choix du dossier), Y-02 (chiffre et déchiffre tout par ce module), Y-06 (écrans du QR, lot Y3).

## Rappel PRD (section 4, M15 ; sections 7 et 8)

| ID | User story | Critères d'acceptation |
| --- | --- | --- |
| Y-08 | Mes données dans iCloud sont chiffrées | Journaux et instantané chiffrés (AES-256-GCM) ; clé créée au premier appairage, transmise du PC à l'iPhone par QR code, gardée dans le coffre de chaque appareil, jamais dans iCloud ; clé de secours imprimable |

Écarts au PRD déjà inscrits (docs/decisions.md, ADR 0011 « Conséquences ») : chiffrement en Rust (`aws-lc-rs`) et non en Web Crypto ; la clé passe par une WebView en deux points encadrés (§2.1) ; fichiers nommés par appareil et par segment.

## Références visuelles

- PC-Appairage.html : avertissement « Ce code transmet la clé de chiffrement de vos données. Il ne passe jamais par iCloud. », « Clé de secours », « Imprimer la clé de secours », « Annuler », « Code valable 5 minutes · Nouveau code ». ## Critères testables

Références : ADR 0011 §1.2, §2, §2.1, §2.2, §2.3, §10.3, §11.1, §12. Tests : `cargo test` (`src-tauri/tests/desktop/sync_*.rs`, `config.rs`) et Vitest (codec de référence `tests/sim/syncCodec.ts`).

1. **Étant donné** un enregistrement en clair, **quand** Rust le chiffre, **alors** la ligne est `<sm>.<sv>.<base64url(nonce 12 octets ‖ texte chiffré ‖ étiquette 16 octets)>` en AES-256-GCM (`aws_lc_rs::aead::RandomizedNonceKey`, nonce tiré par la bibliothèque, jamais fourni par le code) ; deux chiffrements du même texte donnent deux lignes différentes ; le déchiffrement redonne le texte (§1.2, §2).
2. **Étant donné** un texte clair de 1 octet ou de 5 000 octets, **alors** il est bourré à `longueur JSON (u32 gros-boutiste) ‖ JSON ‖ zéros` jusqu'au multiple de 4 Kio supérieur (4 Kio au minimum) ; le lecteur vérifie la longueur annoncée et la nullité du bourrage, tout écart est une corruption ; **alors** les octets d'un fichier chiffré ne contiennent ni le titre d'une tâche de test, ni aucun nom de table (recherche d'octets : absent) (§1.2, §1.5).
3. **Étant donné** un enregistrement chiffré, **quand** il est déplacé dans un autre segment, réordonné, recopié dans un autre fichier ou d'un autre appareil, ou que son `sm` / `sv` d'en-tête est changé, **alors** le déchiffrement échoue ; de même pour un `state.ctx` d'une autre époque ou d'un autre `stateSeq` (AAD préfixée par la longueur de chaque champ : journal, instantané, état) (§2).
4. **Alors** `tests/fixtures/sync/vectors.json` est vérifié par `cargo test` **et** par Vitest (codec de référence Web Crypto de Node) : bourrage, AAD préfixée, `kid`, `encryptedLineBytes` (plus petit enregistrement, enregistrement de 256 Kio, chiffres de `sm` et `sv`) égal à la longueur réelle de la ligne Rust ; segment d'exactement 1 Mio accepté et 1 Mio + 1 octet refusé (`segment-full`) ; appel d'ajout d'exactement 1 Mio accepté et 1 Mio + 1 refusé (`too-large`) (§1.3, §12, avenant « Amorce »).
5. **Étant donné** une clé `K` de 32 octets aléatoires (`SystemRandom`), **alors** `K_rec` et `kid` sont dérivés par HKDF-SHA256 (sel `"circletasks"`, `info` `ct/1 records` et `ct/1 kid`), `kid` = 16 caractères hexadécimaux qui ne révèlent rien de `K` ; `K` et ses dérivées vivent dans des `Zeroizing` sans `Debug` ni `Serialize` (test de compilation) (§2).
6. **Étant donné** le coffre (`vault.rs`, entrée `fr.circletasks.planner` / `circletasks.sync.key.v1`, valeur en base64), **quand** `sync_key_create` est appelée, **alors** elle renvoie `{ kid }` ; une seconde fois : `key-exists` ; sur un dossier qui contient déjà des données CircleTasks (un dossier `devices/<uuid>/` avec un fichier `ct-*` d'en-tête valide, y compris dans le nuage) : `folder-has-data`, aucune clé écrite ; `sync_key_status` renvoie `{ present, kid }` sans jamais la clé (§2.2, §10.3).
7. **Alors** `K` n'est écrite ni dans SQLite, ni dans le dossier iCloud, ni dans un journal technique : après un scénario complet de création, aucun fichier du dossier de test ni aucune table de la base de test ne contient les 32 octets (ni leur base64) ; le déplacement `calendars/vault.rs` → `vault.rs` ne change aucun comportement des agendas (tests K-01 inchangés et verts) (§2, §2.2).
8. **Étant donné** la clé de secours (`K` + 2 octets `SHA-256(K)[0..2]`, base32 Crockford, groupes de 5 caractères préfixés `CT1-`, 55 caractères utiles), **alors** l'aller-retour redonne `K` ; la saisie tolère la casse, les espaces, les tirets, `O`/`0`, `I`/`L`/`1` ; une somme de contrôle fausse est refusée (`invalid-pairing`) ; le décodage se fait en Rust seulement (§2).
9. **Étant donné** un fichier dont le `kid` d'en-tête diffère du `kid` local, **alors** il n'est pas déchiffré et l'appareil qui l'a écrit est marqué `foreign` (statut par appareil, jamais global) ; `key-mismatch` global seulement si aucun appareil connu ne partage la clé locale (§2, §3.4).
10. **Étant donné** une demande d'affichage de la clé, **quand** `sync_pairing_open({ mode: 'show' })` est appelée, **alors** Rust ouvre la confirmation native (`consent.rs`, trait `Consent` injectable) : `TaskDialogIndirect`, propriétaire `main`, deux boutons « Afficher la clé » / « Annuler », `nDefaultButton == IDCANCEL` (fonction pure de configuration testée) ; textes lus dans `src/i18n/native/fr.json` compilé par `include_str!`, jamais fournis par la WebView ; refus ou fermeture : `consent-denied`, aucune fenêtre créée, aucune clé renvoyée (§2.1).
11. **Étant donné** `main` non visible, réduite ou pas au premier plan, **alors** `consent-denied` sans boîte ; **étant donné** les compteurs persistés (`sync/consent.json`, écriture `.tmp` + renommage) : 3 affichages et 5 imports par 10 minutes (toute ouverture compte, refus compris), 10 minutes de blocage après un refus, relus après un redémarrage simulé (`process:allow-restart` ne remet rien à zéro), fichier illisible = bloqué 10 minutes, une seule boîte à la fois (appel pendant une boîte ouverte : `rate-limited`) (§2.1).
12. **Alors** la fenêtre `pairing` n'est **jamais** déclarée dans `tauri.conf.json` et n'est créée que par Rust ; `sync_pairing_open` ne réutilise jamais une fenêtre existante (libellé occupé avant la boîte ou pendant : `consent-denied`, aucune fenêtre, aucun jeton) ; `sync_pairing_payload`, `sync_key_import` (PC) et `sync_pairing_close` vérifient libellé, URL exacte (`pairing.html` ; l'URL du serveur Vite seulement sous `cfg(debug_assertions)`, refusée par un test en `--release`), HWND de l'instance créée par Rust et jeton à usage unique lié à l'instance et à la génération, sinon `wrong-window` ; le mode `show` / `import` est lié à l'instance (`wrong-mode`) ; `sync_pairing_close` ne détruit que la fenêtre appelante ; la croix native (`CloseRequested`) détruit la fenêtre (§2.1).
13. **Alors** la fenêtre `pairing` est créée masquée, `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` est appliquée sur le fil propriétaire (`run_on_main_thread`), le retour est vérifié avant l'affichage (échec : fenêtre détruite, `io`, rien renvoyé), la fenêtre `main` n'est jamais concernée ; un seul minuteur de 5 minutes par génération : un ancien minuteur est sans effet après « Nouveau code » ; réduction ou perte de visibilité de `main` : fenêtre détruite (§10.3). Ces garanties sont testées avec une fenêtre de test du même libellé (autre URL, autre HWND) ; la page `pairing.html` réelle arrive avec Y-06.
14. **Étant donné** `sync_key_import` (`{ qrText }` ou `{ recoveryKey }`), **alors** un dossier configuré est exigé (`not-configured` sinon) ; Rust décode la clé, calcule son `kid` et lit les en-têtes **avant** d'enregistrer : aucun fichier de ce `kid` → `key-mismatch`, rien d'enregistré ; dossier encore vide → `cloud-pending` ; QR dont l'heure `x` est dépassée de plus de 2 minutes → `pairing-expired` ; une **autre** clé déjà au coffre → confirmation native « Remplacer la clé de synchronisation de cet appareil ? » dont la fenêtre appelante est propriétaire (refus : `consent-denied`) ; même clé : sans effet ; fenêtre appelante non visible ou pas au premier plan : `consent-denied` ; limite persistée de 5 appels par 10 minutes ; tampons effacés (`zeroize`) après l'écriture au coffre (§10.3, §2.1).
15. **Alors** `config.rs` vérifie les six contrôles de l'ADR 0011 §11.1 : (1) `generate_handler!` = `AppManifest::commands` de `build.rs` ; (2) `sync.json` : exactement les 18 permissions de `main`, sans `sync_pairing_payload`, `sync_key_import` ni `sync_pairing_close` ; (3) `sync-pairing.json` : exactement ces trois, fenêtre `pairing`, sans clé `webviews`, aucune permission `core:` ; (4) aucune autre capability n'accorde `sync-*` ; (5) aucune capability qui s'applique à `main` (jokers, `webviews`, ensembles `*:default` développés par `acl-manifests.json`) n'accorde `core:webview:allow-create-webview-window`, `core:webview:allow-create-webview` ni `core:window:allow-create` ; (6) `focus-launcher.json` n'accorde que `allow-focus-window-open`, `allow-focus-window-bring-to-front` et `allow-focus-window-close`. **Correctif F-01 (troisième audit H1)** : la mini-fenêtre Focus passe par `focus_window.rs` (libellé `focus`, URL `index.html?window=focus` et options fixées par Rust, position recentrée si hors écran), `tauriFocusWindow.ts` appelle ces commandes et le comportement de F-01 est inchangé (tests `focus.rs` et Vitest).
16. **Alors** aucun journal technique (Rust et TypeScript), aucun état Zustand, aucun message de `SyncPlatformError` ne contient `K`, `qrText`, la clé de secours, la saisie, un titre de tâche ni un chemin complet ; test de simulation qui capture tous les journaux et l'état des stores pendant un appairage complet ; `SyncPlatformError` ne recopie jamais l'entrée d'une commande (§2.3, §12).
17. **Étant donné** la cible iOS, **alors** `vault_ios.rs` n'accepte que les comptes `circletasks.sync.key.*` (dont `.next`) et leur applique toujours `sync_key_attributes()` (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, `kSecAttrSynchronizable = false`, via `security-framework`) ; test `cargo test` des constantes sur toutes les cibles, compilation iOS par `.github/workflows/build-ios.yml` (aucune commande iOS locale) (§2.2).
18. **Étant donné** le budget de nonces, **alors** chaque appareil compte les enregistrements scellés (`sync/usage.json`) ; alerte au-delà de 2^30 (somme des têtes publiées), `key-exhausted` à 2^32 (seuils injectables dans les tests) (§2).
19. **Alors** les dépendances directes `aws-lc-rs` 1, `zeroize` 1 et `security-framework` (cible iOS, version alignée sur `keyring`, à confirmer par `cargo tree --target aarch64-apple-ios`) sont ajoutées sans nouvelle entrée dans `Cargo.lock` ; `docs/licences.md` est complété ; `cargo audit` (`audit-rust` de `tests.yml`) passe.

### Défauts relevés par la QA (non corrigés ; tests `#[ignore]` ou `it.fails` en attente de correctif)

- QA-Y1-1 (faible) : `MasterKey::seal` (`src-tauri/src/sync/crypto.rs`) accepte `sm` / `sv` de plus de 6 chiffres alors que `parse_line_prefix` les refuse à la relecture : une ligne scellée avec `sv >= 1 000 000` serait écrite puis illisible. Test : `sync_qa_crypto.rs`, `y08_1_seal_refuses_a_version_the_reader_cannot_parse` (ignoré). **Corrigé** (« Y-08: corrections revue et audit ») : `seal` refuse `sm` / `sv` hors de 1 à 999 999 (`CryptoError::BadVersion`), test réactivé.
- QA-Y1-4 (faible, codec de test seulement) : le codec TypeScript de référence accepte des entrées que Rust refuse (espace insécable, `ı` et `ſ` dans la clé de secours, absence du plafond de 256 octets, clé JSON répétée et `x: 1.0` dans le QR). Tests : `syncCodecQa.test.ts` (2 `it.fails`). **Corrigé** : le codec applique les règles de Rust (majuscules et espaces ASCII seulement, 256 octets, `hasStrictJsonShape` sur le QR), tests réactivés.
